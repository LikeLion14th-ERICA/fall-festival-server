# 재학생존 운영시간 설정 · 프런트 전달 문서

[API v2 목차](README.md) · [전체 프런트 안내](FRONTEND.md) ·
[OpenAPI](openapi.json) · [제품 요구사항](../docs/wiki/product/admin/crowd.md)

대상: 관리자 화면의 날짜별 재학생존 운영시간 조회·저장 기능(`ADM-CROWD-002`).
아래 날짜와 시간은 가상 예시입니다. 실제 날짜 목록과 초기값은 서버에서 조회합니다.
백엔드 API를 연동하는 실제 UI 구현은 프런트 담당 범위입니다.

## 1. API와 조회 데이터

모든 경로는 `ADMIN` 인증이 필요합니다. 관리자 요청 제한을 적용하며 성공·오류 응답 모두
`Cache-Control: no-store`입니다. 쿼리 파라미터는 사용하지 않습니다.

| 동작 | 메서드·경로 | 성공 응답 |
|---|---|---|
| 날짜 목록 | `GET /api/v2/admin/crowding/operating-hours` | `200`, `data.items` 배열 |
| 날짜 상세 | `GET /api/v2/admin/crowding/operating-hours/{operatingDay}` | `200`, `data` 객체와 strong `ETag` |
| 날짜 저장 | `PUT /api/v2/admin/crowding/operating-hours/{operatingDay}` | `204`, 응답 본문 없음 |

목록은 게시된 축제일만 `operatingDay` 오름차순으로 반환합니다. 클라이언트 달력이나 공개
혼잡도 응답으로 편집 날짜를 만들지 않습니다. 게시 날짜가 없으면 `200`과 `data.items: []`입니다.
목록의 각 항목과 상세의 `data`는 다음 구조입니다.

| 응답 필드 | 타입 | 의미 |
|---|---|---|
| `operatingDay` | `string` (`YYYY-MM-DD`) | 편집할 운영일 |
| `opensAt` | `string \| null` | 적용 중인 KST 시작 시각 |
| `closesAt` | `string \| null` | 적용 중인 KST 종료 시각 |
| `updatedAt` | `string \| null` | 운영시간 설정 수정 시각. `null`이면 관리자 저장 전 카탈로그 초기값 |

동적 관리자 응답의 `meta.revision`은 `0`입니다. 조회값은 KST로 반환합니다. 잘못된 카탈로그
초기값은 초가 포함된 값이나 `null`도 그대로 반환하므로 임의로 반올림하거나 채우지 않습니다.
원래 값을 표시하고 관리자가 유효한 시간으로 수정할 수 있게 합니다.

## 2. Request body

운영일은 URL의 `{operatingDay}`로 지정합니다. **본문에는 `opensAt`, `closesAt` 두 필드만**
보냅니다. 두 필드 모두 필수이며 `operatingDay`, `updatedAt` 등 추가 필드는 허용하지 않습니다.

| 필드 | 타입 | 입력 규칙 |
|---|---|---|
| `opensAt` | `string` | offset 포함 RFC3339. KST 기준 운영일 당일 `00:00` 이상, 익일 `00:00` 미만 |
| `closesAt` | `string` | offset 포함 RFC3339. 시작보다 늦고 **익일 KST `01:00` 이하** |

분 단위로 입력하고 초는 반드시 `:00`을 붙입니다. `.000`을 포함한 모든 소수초는 금지합니다.
`Z`나 다른 offset도 받지만 서버는 Asia/Seoul 기준으로 정규화해 날짜와 범위를 검사합니다.
KST `datetime-local` 값 `2030-10-01T20:00`은 `2030-10-01T20:00:00+09:00`으로 조합합니다.
`Date.toISOString()`은 소수초가 붙으므로 결과를 그대로 보내지 않습니다.

다음 예시는 모두 `PUT /api/v2/admin/crowding/operating-hours/2030-10-01`의 본문입니다.

**당일 종료**

```json
{
  "opensAt": "2030-10-01T20:00:00+09:00",
  "closesAt": "2030-10-01T22:00:00+09:00"
}
```

**익일 00:30 종료** — 종료 날짜를 다음 날짜로 보냅니다.

```json
{
  "opensAt": "2030-10-01T20:00:00+09:00",
  "closesAt": "2030-10-02T00:30:00+09:00"
}
```

**허용되는 마지막 종료 시각: 익일 01:00**

```json
{
  "opensAt": "2030-10-01T20:00:00+09:00",
  "closesAt": "2030-10-02T01:00:00+09:00"
}
```

시작 순간은 운영에 포함하고 종료 순간은 제외합니다. 마지막 예시는 익일 `01:00` 직전까지
운영 중이며 `01:00`부터 종료입니다. 익일 `01:01`, 운영일 밖의 시작, 시작 이하의 종료,
0이 아닌 초, 소수초, 필수 필드 누락·추가 필드는 `422 VALIDATION_FAILED`입니다.

## 3. 요청 헤더와 저장 순서

| 헤더 | 사용 시점 | 값 |
|---|---|---|
| `Authorization` | 모든 요청 | 관리자 `Bearer <accessToken>` |
| `Content-Type` | PUT | `application/json` |
| `If-Match` | PUT, 필수 | **해당 날짜 상세 GET의 strong `ETag` 원문**. 따옴표도 그대로 유지 |
| `Idempotency-Key` | PUT, 필수 | 새 저장마다 발급한 키. 예: `crypto.randomUUID()` |
| `If-None-Match` | GET 조건부 재조회 | 해당 조회에서 보관한 `ETag` |

1. 화면 진입 시 목록을 조회합니다. 날짜별 편집 진입 시 상세를 조회해 시간과 ETag를 보관합니다.
2. 입력을 검증하고 저장 시점의 **본문·ETag·Idempotency-Key를 한 묶음으로 보관**합니다.
3. 해당 날짜에 PUT을 보냅니다. 목록 ETag나 공개 혼잡도 ETag를 `If-Match`로 사용하지 않습니다.
4. `204`이면 성공입니다. 빈 응답에 `response.json()`을 호출하지 않습니다.
5. 성공 후 목록·해당 날짜 상세·현재 혼잡도(`GET /api/v2/crowding`)를 다시 조회합니다.

ETag는 HTTP 응답 헤더에서 읽습니다. 조건부 GET의 `304`는 본문이 없으므로 보관한 조회값을
사용합니다. 보관한 조회값이 없으면 `If-None-Match` 없이 다시 조회합니다.

네트워크 오류 등으로 완료 여부가 불명확하면 **같은 본문·ETag·키로 재시도**합니다.
완료된 동일 요청은 `204`를 다시 반환하며, 이후 해당 날짜가 게시에서 제거돼도 같습니다.
같은 키에 다른 본문을 보내면 충돌합니다. 값을 다시 편집해 저장할 때는 새 키를 발급합니다.

## 4. 오류 처리

| HTTP · 코드 | 원인 | 프런트 처리 |
|---|---|---|
| `400 INVALID_DATE` | 경로 날짜 형식 오류 | `YYYY-MM-DD` 경로 생성 확인 |
| `404 NOT_FOUND` | 상세 조회 날짜가 게시 목록에 없음 | 목록 갱신, 해당 날짜 편집 종료 안내 |
| `409 NOT_FESTIVAL_DAY` | 게시되지 않은 날짜의 새 저장 | 입력 보존, 목록 갱신과 게시 해제 안내 |
| `409 EDIT_CONFLICT` | 저장 기준 ETag가 현재 값과 다름 | 입력 보존, 최신 상세를 별도로 보여 주고 검토 후 재저장 |
| `409 IDEMPOTENCY_KEY_REUSED` | 같은 키에 다른 본문 사용 | 저장 요청 묶음 관리 확인, 새 편집 저장에는 새 키 사용 |
| `428 PRECONDITION_REQUIRED` | `If-Match` 누락 | 상세 ETag 조회 후 요청 구성 |
| `428 IDEMPOTENCY_KEY_REQUIRED` | `Idempotency-Key` 누락 | 저장용 키 발급 후 요청 구성 |
| `422 VALIDATION_FAILED` | 본문·시간 구간 오류 | 필드와 허용 범위 안내, 입력 보존 |

인증·권한·요청 제한 등 공통 오류는 [전체 프런트 안내](FRONTEND.md)와 [OpenAPI](openapi.json)를
따릅니다. 일시 오류에도 입력값과 저장 요청 묶음을 유지하고 재시도를 제공합니다.
충돌 후 최신 ETag를 읽었다고 작성 중인 입력을 자동 교체하거나 자동 저장하지 않습니다.

## 5. 화면 상태와 운영 반영

| 상태 | 구현 요구 |
|---|---|
| 로딩 | 임의 날짜·시간을 채우지 않고 목록·상세 로딩 표시 |
| 정상 | 게시 날짜만 표시, 날짜마다 독립된 저장 버튼 제공 |
| 빈 목록 | 운영일 없음 표시. 공개 API의 일정 미설정 오류로 대신 표시하지 않음 |
| 저장 중 | 해당 날짜의 진행 상태 표시, 입력과 저장 요청 묶음 유지 |
| 검증 실패·일시 실패 | 작성한 값 보존, 오류와 재시도 표시 |
| 충돌 | 작성한 값과 최신 서버 값을 비교할 수 있게 표시 |
| KST 자정 | 현재 운영일·운영 상태 재조회. 달력 날짜만 보고 혼잡도를 초기화하지 않음 |

- 종료 선택지에 `익일 00:30` 등 날짜가 바뀌는 시각과 마지막 경계 `익일 01:00`을 명시합니다.
- 조회 데이터와 편집 입력을 분리해 polling·재조회가 작성 중인 값을 덮어쓰지 않게 합니다.
  사용자 홈은 기존 15초 polling으로 변경된 운영 상태를 반영합니다.
- 오늘 게시 일정이 시작되면 오늘을 우선합니다. 오늘 시작 전에는 전날 운영 구간이 열려 있으면
  전날 `operatingDay`·혼잡도·수정 시각을 유지합니다. 종료 후 표시할 운영일은 서버가 선택합니다.
- 종료를 앞당기면 운영 상태를 다시 계산합니다. 자정 뒤에는 다음 운영일의 `운영 전`이 표시될 수
  있습니다. 다시 연장해 기존 운영일이 선택되고 운영 중이면 그날의 혼잡도·수정 시각을 복원합니다.
  **운영시간 저장 자체는 혼잡도 단계와 혼잡도 수정 시각을 변경하지 않습니다.**
- 관리자 저장 전에는 카탈로그 초기값을 사용합니다. 초기값과 같은 시간을 처음 저장해도 관리자
  설정으로 확정합니다. 이후 같은 값 저장은 운영시간 수정 시각을 바꾸지 않습니다.
- 저장값은 재시작·재게시·게시본 롤백 후에도 유지합니다. 게시에서 빠진 날짜는 목록에서 숨기되
  설정은 보존하고, 다시 게시하면 재적용합니다. 새 날짜는 카탈로그 초기값으로 시작합니다.
